# Production Launch Recipe

This document describes the validated DeepSeek-V4-Flash-0731 serving recipe in
this checkout. It explains the effective vLLM arguments, why they are present,
and which claims are validated on the target hardware.

This is a recipe for the reasoning-tree checkout, not a generic vLLM profile.
Do not apply it to the separate `/home/az04297/re-SuperInfer/vllm-modern`
checkout or to hardware with a different GPU/NUMA topology without validating
the resulting configuration.

## Launch Path

Operators normally use only:

```bash
cd /home/az04297/re-SuperInfer/vllm-modern-reasoning
CONTAINER_NAME=richard-base-dev-sysnice PORT=8202 bash start.sh
```

The scripts have three runtime boundaries and one configuration source:

1. `config/reasoning-tree-superinfer.env` is the single checked-in source for
   serving defaults. It contains no credentials and supports explicit
   environment overrides using the `${VAR:-default}` pattern.
2. `start.sh` owns operator lifecycle: it loads the config, launches the
   detached container process, waits for `/health`, and sends three short
   sequential warmup requests before reporting `READY`.
3. `scripts/launch_direct_deepseek_superinfer.sh` owns the host-to-container
   boundary. It loads the same config, applies explicit CLI overrides, validates
   the container/port/profile/workdir, and records the effective command and
   profile sidecars next to the server log.
4. `scripts/run_direct_deepseek_server_inside_container.sh` owns the
   container-local runtime. It requires the config values passed by the outer
   launcher and constructs the final
   `.venv/bin/python -m vllm.entrypoints.cli.main serve` command.

The configuration file is the source of serving defaults; log naming is
operator lifecycle metadata generated by `start.sh` (or a deterministic
port-based fallback for direct launcher use). The generated `.cmd` and
`.profile` sidecars are the source of truth for what a particular launch
actually used. The inner script intentionally has no independent production
defaults, so a missing handoff fails fast instead of silently creating a
different recipe.

For a controlled diagnostic override, use environment variables or the outer
launcher CLI rather than editing multiple scripts:

```bash
MAX_NUM_SEQS=8 \
  bash scripts/launch_direct_deepseek_superinfer.sh \
    --config config/reasoning-tree-superinfer.env \
    --dry-run
```

The operator entrypoint accepts the same configuration selection:

```bash
bash start.sh --config config/reasoning-tree-superinfer.env
```

Do not use diagnostic overrides for the validated production profile without
recording the changed values and rerunning the relevant validation.

The launch is intentionally detached from the shell. Use `stop.sh` for
shutdown; do not use a broad `pkill` command.

For automatic production recovery, use the separate user-service control
command `deepseek-vllmctl`. This command is intentionally different from the
native `.venv/bin/vllm` CLI. The user systemd unit is
`deepseek-vllm.service`; installation does not enable or start it.

```bash
scripts/deepseek-vllmctl install
deepseek-vllmctl status
```

Enable automatic recovery only after reviewing the service and confirming that
port `8202` is not owned by another operator:

```bash
deepseek-vllmctl enable
deepseek-vllmctl start
```

During development, pause supervision before manual launch/benchmark/stop
cycles:

```bash
deepseek-vllmctl pause
# edit code, run benchmarks, and use start.sh/stop.sh manually
deepseek-vllmctl resume
```

`pause` creates a user-owned maintenance hold and stops only the scoped
DeepSeek vLLM process. It does not stop or reconfigure the Docker container.
The unit uses bounded systemd restart backoff and stops retrying after repeated
failures; see `systemd/deepseek-vllm.service` and `scripts/run_supervised.sh`.

The in-container launcher keeps a small process-local supervisor around the API
child. It does not restart the server or act as a watchdog. Its only purpose is
to write the API child PID and final exit code/signal to the server log. The API
and CLI signal handlers also log received `SIGTERM`/`SIGINT` names. This lets an
incident distinguish a logged graceful request, an unexpected nonzero exit, and
signal-based termination without changing host services. It cannot identify an
external process that sent an unlogged `SIGKILL`.

## Effective Recipe

The following is the conceptual final command. The scripts also set offline
model-cache paths, logging, RPC, tokenizer, and NCCL environment variables
inside the container.

```text
.venv/bin/python -m vllm.entrypoints.cli.main serve \
  /workspace/re-SuperInfer/models--deepseek-ai--DeepSeek-V4-Flash-0731/snapshots/<validated-snapshot> \
  --trust-remote-code \
  --host 0.0.0.0 \
  --port 8202 \
  --served-model-name deepseek-ai/DeepSeek-V4-Flash-0731 \
  --tensor-parallel-size 2 \
  --pipeline-parallel-size 1 \
  --enable-expert-parallel \
  --disable-custom-all-reduce \
  --gpu-memory-utilization 0.92 \
  --max-model-len 1048576 \
  --max-num-seqs 24 \
  --max-num-batched-tokens 32768 \
  --block-size 256 \
  --tokenizer-mode deepseek_v4 \
  --reasoning-parser deepseek_v4 \
  --tool-call-parser deepseek_v4 \
  --enable-auto-tool-choice \
  --kv-cache-dtype fp8 \
  --compilation-config '{"cudagraph_mode":"FULL_AND_PIECEWISE","custom_ops":["all"]}' \
  --attention-config '{"use_fp4_indexer_cache":false}' \
  --max-cudagraph-capture-size 128 \
  --enable-prefix-caching \
  --download-dir /workspace/re-SuperInfer \
  --swap-cpu-memory-gb 128 \
  --pin-memory-fix \
  --proactive-swap-budget 2400 \
  --capacity-wait-timeout 30 \
  --vlt-alpha 3 \
  --vlt-beta-bandwidth 1 \
  --vlt-beta-future 1 \
  --slo-ttft 5 \
  --slo-tbt 0.1 \
  --gh200-topology-tuned \
  --local-cpu-pool-fraction 0.75 \
  --local-swap-bandwidth-bytes-per-s 966367641600 \
  --remote-swap-bandwidth-bytes-per-s 300647710720 \
  --numa-bind \
  --numa-bind-nodes 0 1
```

The actual snapshot path is controlled by `MODEL_PATH` in the inside-container
launcher. The command and the resolved profile are recorded in the `.cmd` and
`.profile` sidecars for each launch.

## Argument Reference

### Model And API

| Argument | Meaning and reason |
|---|---|
| Model path | Uses the local DeepSeek-V4-Flash-0731 snapshot. Offline cache variables prevent an unexpected network fetch during startup. |
| `--trust-remote-code` | Allows the model's repository-defined configuration/model code required by DeepSeek-V4. Only use with a trusted local model snapshot. |
| `--host 0.0.0.0` | Makes the API reachable through the container network. The operator health check still targets `127.0.0.1` inside the container. |
| `--port 8202` | Production reasoning-tree API port. `start.sh` and `stop.sh` both scope their process handling to this port by default. |
| `--served-model-name` | Sets the model identifier clients must send in API requests. It does not rename or copy model weights. |
| `--tokenizer-mode deepseek_v4` | Selects the DeepSeek-V4 tokenizer implementation and its special-token behavior. |
| `--reasoning-parser deepseek_v4` | Parses DeepSeek-V4 reasoning output for the OpenAI-compatible API. |
| `--tool-call-parser deepseek_v4` | Parses DeepSeek-V4 tool-call output. |
| `--enable-auto-tool-choice` | Allows the server to select and emit tool calls when the request/tool parser path supports them. |
| `--download-dir /workspace/re-SuperInfer` | Points vLLM/Hugging Face cache resolution at the shared local model directory. |

### Parallelism And Communication

| Argument | Meaning and reason |
|---|---|
| `--tensor-parallel-size 2` | Splits model tensor work across both GH200 GPUs. This is the validated two-GPU layout. |
| `--pipeline-parallel-size 1` | Does not split the model into pipeline stages. With two GPUs, tensor parallelism carries the model distribution. |
| `--enable-expert-parallel` | Distributes DeepSeek MoE expert computation using expert-parallel handling instead of treating all expert work as ordinary replicated tensor-parallel work. |
| `--disable-custom-all-reduce` | Uses the standard collective path instead of vLLM's custom all-reduce implementation. This was selected for the validated GH200/DeepSeek setup and avoids relying on a custom communication path that was not part of the accepted run. |
| `--numa-bind` | Binds GPU worker subprocesses to the NUMA node associated with each GPU. This keeps CPU-side scheduler, tokenizer, and offload work closer to the GPU it serves. |
| `--numa-bind-nodes 0 1` | Explicitly maps visible GPU rank 0 to NUMA node 0 and rank 1 to NUMA node 1. The list must cover every visible GPU. |

### Memory, KV Cache, And Request Shape

| Argument | Meaning and reason |
|---|---|
| `--gpu-memory-utilization 0.92` | Gives vLLM a 92% GPU-memory planning target. The remaining headroom reduces startup/runtime allocation risk; it is not a promise that 92% will be continuously used. |
| `--max-model-len 1048576` | Maximum accepted input-plus-output sequence length: 1,048,576 tokens. It is an admission/configuration limit, not a request to reserve a 1M-token KV cache at startup. |
| `--max-num-seqs 24` | Maximum number of simultaneously scheduled sequences. This matches the validated 24-user pressure shape. Higher values increase concurrency but also increase scheduler and KV pressure. |
| `--max-num-batched-tokens 32768` | Maximum tokens scheduled in one batch step. It bounds per-step work and supports the tested long-context/decode mixture. |
| `--block-size 256` | KV cache page size in tokens. Larger pages reduce block-management overhead but make allocation granularity coarser; `256` is the validated DeepSeek setting. |
| `--kv-cache-dtype fp8` | Stores GPU KV cache in FP8 to increase effective KV capacity and reduce KV traffic while the model computation remains on its configured model dtype path. |
| `--enable-prefix-caching` | Reuses KV blocks for matching prompt prefixes. The SimpleCPUOffloadConnector requires prefix caching to be enabled. |
| `--swap-cpu-memory-gb 128` | Enables the SimpleCPUOffloadConnector with a 128 GiB CPU KV budget across the TP world. With TP=2 this is approximately 64 GiB per rank. |
| `--pin-memory-fix` | Enables the validated host-memory allocation workaround. The worker allocates CPU storage and applies the required host registration path rather than relying on the problematic large pinned allocation behavior. |

The current DeepSeek path uses a GPU-derived CPU-KV layout. `--swapper-block-first`
is deliberately disabled because block-first is not validated for DeepSeek-V4
and the layout selector forces DeepSeek-V4 back to `gpu_derived` unless the
unsupported high-risk override is used.

### CUDA Graphs And Attention

| Argument | Meaning and reason |
|---|---|
| `--compilation-config cudagraph_mode=FULL_AND_PIECEWISE` | Enables full CUDA graphs where decode shapes are suitable and piecewise graphs for compatible execution regions. This reduces repeated launch overhead after capture and is the main steady-state latency optimization in this recipe. |
| `custom_ops=["all"]` | Enables vLLM custom operation dispatch in the compilation configuration. This keeps optimized registered kernels available rather than forcing native fallbacks. |
| `--max-cudagraph-capture-size 128` | Caps the largest CUDA-graph capture batch size at 128. It limits capture memory/time while covering the validated serving batch range. |
| `--attention-config '{"use_fp4_indexer_cache":false}'` | Disables the optional FP4 indexer cache for this validated DeepSeek run. This avoids adding an unvalidated cache representation to the attention path. |
| `--enforce-eager` | Not passed by the production recipe, equivalent to `enforce_eager=false`. CUDA graph and compiled execution remain available. Setting it to true is a debugging/compatibility choice and generally sacrifices steady-state speed. |

CUDA graph capture and model initialization still happen during startup. The
three short API warmup requests in `start.sh` are separate: they prime the
actual API/tokenizer/decode path for the first users, but they are not a
substitute for CUDA graph capture or pressure validation.

### CPU-KV Offload And Scheduler

| Argument | Meaning and reason |
|---|---|
| `--proactive-swap-budget 2400` | Sets the maximum target scan/movement budget in KV blocks for lazy proactive offload. When waiting work needs GPU KV capacity, the scheduler can proactively move eligible KV blocks toward CPU storage. |
| `--capacity-wait-timeout 30` | Allows a capacity-blocked request to wait up to 30 seconds without progress before it is classified as a stale-capacity failure condition. Ordinary queueing while work is progressing is not treated as stale capacity. |
| `--vlt-alpha 3` | Weights predicted time-between-token (TBT) SLO penalty in proactive victim scoring. Larger values make the scheduler more sensitive to decode smoothness. |
| `--vlt-beta-bandwidth 1` | Weights estimated swap-time cost in proactive victim scoring. It discourages choices whose movement is predicted to be expensive. |
| `--vlt-beta-future 1` | Weights time already spent and predicted future delay in proactive victim scoring. It helps avoid repeatedly disadvantaging requests that have waited longer. |
| `--slo-ttft 5` | TTFT target in seconds used by the proactive scoring penalty. It is a scheduling preference, not an API timeout or hard SLA guarantee. |
| `--slo-tbt 0.1` | TBT target in seconds used by proactive scoring. It is not a hard per-token enforcement limit. |
| Lazy offload | The connector records/stores KV as needed and uses proactive movement under pressure instead of eagerly copying every request immediately. This reduces unnecessary transfer work in ordinary serving. |
| Full-sequence capacity checking | The scheduler checks whether the full request sequence can fit before admission, preventing chunked-prefill over-admission and KV thrashing. |

VLT means the local Variable Latency/TBT-aware victim-scoring logic in this
checkout. The coefficients influence scheduler ranking; they do not create a
separate transfer engine or guarantee a particular TTFT/TBT.

### GH200 Topology And Locality

| Argument | Meaning and reason |
|---|---|
| `--gh200-topology-tuned` | Enables the GH200 locality-aware offload mode. At worker initialization it discovers GPU PCI/NUMA information with `nvidia-smi` and sysfs, parses GPU peer connectivity into topology islands, and creates locality metadata for CPU KV block ownership. |
| `--local-cpu-pool-fraction 0.75` | Treats up to 75% of each topology island's logical CPU KV pool as local-first capacity. It is a placement policy, not a reservation of 75% of all host RAM. |
| `--local-swap-bandwidth-bytes-per-s 966367641600` | Estimated local GPU/CPU swap bandwidth used as a cost hint, approximately 900 GiB/s in binary units. It is not a bandwidth limit and is not a measured guarantee. |
| `--remote-swap-bandwidth-bytes-per-s 300647710720` | Estimated remote swap bandwidth cost hint, approximately 280 GiB/s in binary units. A lower value makes remote placement appear more expensive to victim scoring. |

In practical terms, the tuned mode tries to assign CPU KV blocks near the GPU
island that will use them, records local/remote placement, counts remote
fallbacks, and adds an estimated remote-transfer penalty to proactive scoring.
It does not rewire PCIe/NVLink, change CUDA's physical memory fabric, or make
remote memory local. If topology discovery is unavailable, the connector logs
a fallback and continues with a conservative logical mapping; inspect the
`offload_gh200_topology_discovered` and
`offload_gh200_topology_fallback_mode` metrics.

This locality mode is complementary to `--numa-bind`: topology tuning decides
logical CPU-KV placement/cost, while NUMA binding controls where worker CPU
execution and memory policy are placed.

### Safety And Experimental Flags

| Setting | Production value | Meaning |
|---|---:|---|
| `--superinfer-high-risk-mode` | disabled | Keeps conservative scheduler and layout safety gates. Enabling it relaxes gates for throughput experiments and can activate otherwise blocked block-first behavior. It is not part of the accepted production profile. |
| `--swapper-block-first` | disabled | Requests a block-first CPU-KV layout. It is not active for DeepSeek-V4 in normal mode because the layout selector forces a safe GPU-derived fallback. |
| speculative tokens | `0` | No speculative configuration is passed. Native DSpark/MTP speculative decoding is not validated in this tree. |
| `DISTRIBUTED_EXECUTOR_BACKEND` | unset | Uses the default local multiprocessing executor for this single-node TP deployment. Set a backend only with a separately validated topology and launch procedure. |
| `GENERATION_CONFIG` | unset | Does not override the model generation configuration at launch. Request-level generation parameters remain available through the API. |

## Startup Warmup

After `/health` responds, `start.sh` sends three sequential short completion
requests by default:

| Variable | Default | Purpose |
|---|---:|---|
| `WARMUP_ENABLED` | `1` | Enables operational warmup. |
| `WARMUP_REQUESTS` | `3` | Number of sequential warmup requests. |
| `WARMUP_MAX_TOKENS` | `8` | Small decode budget to avoid large startup KV pressure. |
| `WARMUP_TIMEOUT_S` | `120` | Per-request timeout. |
| `WARMUP_MODEL` | `deepseek-ai/DeepSeek-V4-Flash-0731` | Model name sent in the warmup request. |

Warmup primes the tokenizer, API routing, model execution, and short decode
path so the first user request is less likely to pay one-time initialization
costs. It is intentionally not a long-context or CPU-KV pressure test. The
script reports `READY` only after warmup succeeds and invokes the scoped
`stop.sh` cleanup path if launch, readiness, or warmup validation fails.

Startup failure diagnostics are opt-in and do not add work to healthy startup:

```bash
COLLECT_START_FAILURE_DIAGNOSTICS=1 \
  bash start.sh --config config/reasoning-tree-superinfer.env
```

If enabled, a failed launch captures process ancestry, container state, GPU and
CUDA/NVML visibility, `/dev/shm` usage, kernel GPU/OOM messages, endpoint state,
and bounded log tails before cleanup. The snapshot intentionally excludes the
container environment so credentials are not copied into incident artifacts.
The `resource_tracker` warnings seen after an abnormal parent exit refer to
Python IPC bookkeeping; investigate them by comparing repeated `/dev/shm`
snapshots rather than assuming they represent a GPU or host-memory leak.

To disable it for a controlled diagnostic launch:

```bash
WARMUP_ENABLED=0 CONTAINER_NAME=richard-base-dev-sysnice PORT=8202 \
  bash start.sh
```

## Verification After Launch

```bash
curl -fsS http://127.0.0.1:8202/health
curl -fsS http://127.0.0.1:8202/v1/models
```

For actual CPU-KV pressure and reload validation, use:

- `scripts/run_heavy_offload_soak.py` for exact-token pressure, store/load
  telemetry, capacity behavior, and final health;
- `scripts/validate_offload_reload.py` for deterministic store/evict/reload
  output validation.

Do not infer performance improvements from the launch flags alone. Compare
latency/throughput with an explicitly defined baseline and record the same
prompt lengths, output budgets, concurrency, and hardware topology.

## Shutdown

Use the matching container and port:

```bash
CONTAINER_NAME=richard-base-dev-sysnice PORT=8202 \
  bash stop.sh
```

`stop.sh` sends `SIGTERM` to the API parent first, allowing vLLM's process-local
engine, distributed, CUDA, shared-memory, and CPU-KV cleanup to run. It then
handles captured descendants and orphaned `VLLM::EngineCore`/`VLLM::Worker_*`
processes, using `SIGKILL` only after bounded grace periods. See the canary and
offload staging guides for the full shutdown rationale.
